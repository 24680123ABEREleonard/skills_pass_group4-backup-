Intended Readers

Project stakeholders, developers, testers, reviewers, maintainers, and operators responsible for installing or evaluating SkillPass.

1. Introduction

1.1 Purpose

This Software Requirements Specification (SRS) defines the functional behavior, interfaces, data, constraints, quality expectations, and acceptance conditions for SkillPass. It serves as a shared reference for implementing, testing, demonstrating, and maintaining the project.

1.2 Product Scope

SkillPass is a browser-based, skills-first hiring demonstration platform. Jobseekers maintain a profile of self-reported skills and project evidence, browse open roles, apply, complete an optional role-specific practical challenge, and follow application status. Employers create and manage openings, inspect applicants’ relevant evidence, review challenge submissions, compare candidates using a transparent role-fit score, and update application outcomes.

Public visitors can view the home page and open opportunities, then register or sign in. The project is delivered as a PHP application backed by MySQL/MariaDB and is documented for local operation with XAMPP.

1.3 Goals

  • Give candidates a structured place to present skills and examples of work.
  • Make job requirements and applicant comparisons legible to employers.
  • Support a practical challenge as optional, job-related evidence.
  • Keep the hiring decision under employer control; the score is advisory and not an automated decision.
  • Provide a usable responsive interface for desktop and mobile browser widths.

1.4 Intended Use and Conventions

“Shall” denotes a required system behavior in this baseline. “Implemented” indicates behavior observed in the project. Character limits and enumerated values reflect current server-side validation or database constraints where available. “Out of scope” means the current project does not provide the capability; it is not a commitment that the capability will never be added.

2. Product Overview

2.1 Product Perspective

SkillPass is a server-rendered web application. A single PHP entry point handles GET page selection and POST actions, reads/writes MySQL through PDO, renders HTML, and uses session state for authentication and one-time flash messages. Client-side JavaScript is limited to responsive navigation toggling and confirmation prompts on forms that opt into confirmation. CSS provides layout, visual presentation, and responsive breakpoints.

2.2 Product Functions

  • Public home and public open-role listing.
  • Account registration, sign-in, and sign-out for jobseeker and employer roles.
  • Jobseeker profile editing, skill list maintenance, and project evidence records.
  • Open-role browsing, application submission, challenge response submission, and application tracking.
  • Employer role creation, optional skill requirements and practical challenge, opening status management, applicant review, challenge review, and application status management.
  • Candidate comparison using required-skill overlap, project count, and challenge status.
  • Role-specific dashboards, profile completion indicator, demand-based skill insight, and a WhatsApp contact link.

2.3 User Classes

3. Users and Operating Context

3.1 Runtime Environment

  • Server: PHP 8.0 or later (required by the language features in use), with PDO MySQL and the mbstring extension.
  • Database: MySQL or compatible MariaDB with InnoDB, foreign keys, ENUM types, UTF-8 (utf8mb4), and the SQL features used by the schema.
  • Local reference stack: XAMPP with Apache and MySQL; schema/database name defaults to skillpass.
  • Client: a modern browser supporting HTML5 forms, CSS Grid/Flexbox, responsive media queries, and JavaScript.
  • Configuration: database host, port, name, username, and password may be supplied with DB_HOST, DB_PORT, DB_NAME, DB_USER, and DB_PASSWORD, or changed in config.php.

3.2 General Constraints

  • The user interface and server-side workflows are currently provided in English.
  • Each account has exactly one role: jobseeker or employer.
  • The application uses a single PHP entry point and a relational database; no API contract or separate service tier is specified.
  • Project and submission evidence are external HTTP/HTTPS links; file upload/storage is not implemented.
  • System availability, backups, production hosting, and operational service-level targets are not established by this demo.

4. System Workflows

4.1 Jobseeker Workflow

Public home / open roles -> Register as jobseeker or sign in -> Review dashboard and open roles -> Maintain profile, skills, and project evidence -> Apply once to an open role, with optional cover note -> If the role has a challenge, submit response and optional evidence URL -> Track application and challenge feedback/status -> Employer may shortlist; contact link becomes available to employer

4.2 Employer Workflow

Register as employer or sign in -> Create an opening with title, company, location, work arrangement, description -> Add zero or more required skills and optionally a title+instructions challenge -> Review applicants ordered by role-fit score, then application time -> Inspect profile, skills, project count, cover note, and challenge evidence -> Review challenge as passed or needs work, with optional feedback -> Set application status: in review, shortlisted, not selected, or hired -> Close or reopen the opening

4.3 Public Visitor Workflow

A visitor can browse public open roles and sign in to apply. Registration creates an account, a blank profile record, and an authenticated session. The homepage offers a WhatsApp link to the configured SkillPass contact number.

6. External Interface Requirements

6.1 User Interface

The UI shall provide role-appropriate navigation, labeled forms, inline validation constraints where practical, visible success/error feedback, status badges, and empty states. The layout shall adapt at desktop, tablet, and mobile widths. Candidate comparison shall present the fit score and its component evidence together, with an explicit note that the score is not an automatic hiring decision.

6.2 Hardware Interfaces

No specialized hardware interface is required. Users need a device capable of running a modern web browser and accessing the application server.

6.3 Software Interfaces

  • MySQL/MariaDB through PHP PDO MySQL.
  • Web browser through HTTP/HTTPS using server-rendered HTML forms and pages.
  • WhatsApp link through a browser navigation to wa.me; SkillPass does not integrate with the WhatsApp API.
  • Evidence is linked through user-supplied HTTP/HTTPS URLs; the system does not fetch, scan, host, or validate the contents of linked resources.

6.4 Communications

Requests use standard browser HTTP form submissions. Mutating operations use POST and include a session-bound CSRF token. The application uses redirects after form actions for the user-facing flow. Production TLS termination and deployment networking are environment responsibilities and are not specified by this repository.

7.3 Data Integrity

  • Primary and foreign keys shall preserve entity identity and associations.
  • Deleting a parent user, job, or challenge cascades to dependent records where configured by the schema.
  • Account registration shall use a database transaction for user and profile creation.
  • Job creation shall use a database transaction for job, skill associations, and optional challenge creation.
  • Profile and skill updates shall be committed together in a database transaction.
  • Timestamps use database current time; application display dates use the PHP runtime timezone.

7.4 Retention and Backup

The project defines no retention schedule, data export, archival, backup, or restore workflow. These are deployment/operations decisions and require definition before production use.

8. Business Rules and Matching

8.1 Application Statuses

Stored valueDisplay labelMeaning
submittedSubmittedInitial state assigned when an application is created.
reviewingIn reviewEmployer is reviewing the application.
shortlistedShortlistedCandidate has advanced; employer contact link is exposed.
declinedNot selectedEmployer has marked the application unsuccessful.
hiredHiredEmployer has marked the candidate as hired.

8.2 Challenge Statuses

A challenge submission starts as submitted. The owning employer may change it to passed or needs_work. A resubmission resets the review state and clears prior reviewer feedback. Challenges are optional at job creation.

8.3 Role-Fit Score

The score is calculated per applicant and displayed on a 0-100 scale when all three evidence components are available. Current formula:

skill_score = (matched required skills / total required skills) * 70 project_score = min(number of candidate projects * 5, 20) challenge_score = 10 if passed; 5 if submitted; otherwise 0 fit_score = round(skill_score + project_score + challenge_score)
  • Skill names are compared case-insensitively. Required skills are the denominator; candidate skills that are not required do not increase the score.
  • If a role has no required skills, the skill component is zero. Therefore, a role without required skills may have a maximum score below 100.
  • Project evidence is represented by project count, not a quality assessment or verification result; up to four projects contribute to this component.
  • Challenge status contributes 10 for passed, 5 for submitted, and 0 for no submission or needs work.
  • Candidate ranking is descending score; equal scores are ordered by earlier application timestamp.
  • The score is a comparison aid only and shall not make or imply a hiring decision. It uses no demographic or personal-characteristic attributes.

8.4 Profile Completion and Opportunity Insight

The dashboard completion indicator uses fixed weights for presence of headline, location, summary, at least one skill, and at least one project. The opportunity insight selects a skill absent from the current profile that appears in the most open roles, with alphabetical ordering used to break equal-demand ties.

10. Security and Privacy Requirements

10.1 Authorization

Each protected action shall require an authenticated session and a matching role. Employer-side updates shall additionally be scoped to a role owned by the current employer. Jobseeker profile and application reads shall be scoped to the current account. Public users shall not be able to invoke protected actions successfully.

10.2 Personal Data

The system stores name, email, password hash, role, profile details, skill associations, project evidence URLs, applications, challenge responses, and employer feedback. The employer applicant view limits candidate identity by abbreviating names and withholding email until the application is shortlisted. A production privacy notice, lawful basis, retention period, deletion/export process, and incident process are not defined here.

10.3 Threat and Abuse Boundaries

Evidence URLs point to third-party content and may reveal information when opened. The current system validates URL syntax and scheme but does not verify ownership, safety, accessibility, or content. Operational controls such as rate limiting, account verification, password reset, audit logging, security monitoring, and backup protection are not implemented in the project baseline.

12. Assumptions, Dependencies and Limits

  • Users have access to a supported browser and the application server; employers and jobseekers provide accurate information.
  • Skill labels are self-reported; project count and challenge state are evidence indicators, not independent verification.
  • A candidate's email becomes visible to an employer only after shortlist status is set.
  • Role descriptions, skills, and challenge instructions are authored by employers and are not moderated by the platform.
  • The deployment supplies PHP, required extensions, a compatible SQL server, database credentials, and writable/session-capable runtime settings.
  • Demo accounts and records are seed data for evaluation only; production deployment must change credentials, database settings, and operational practices.
  • The UI does not include role search/filtering, pagination, editing/deleting existing projects or roles, email notifications, password reset, or file uploads.
  • There is no administrator account or administrative moderation console.

13. Future Scope (Not Current Requirements)

The following are candidate enhancements, not capabilities promised by this baseline:

  • Email verification, password recovery, multi-factor authentication, rate limiting, and audit events.
  • Applicant and job search, filtering, pagination, and notification preferences.
  • Candidate-controlled profile visibility, project editing/deletion, and account/data deletion/export workflows.
  • Employer editing/deletion of openings, structured compensation/experience fields, and role expiry.
  • More robust skills taxonomy, evidence review/verification, and challenge evaluation rubrics.
  • Accessibility audit and formal WCAG 2.2 AA target; localization and configurable timezone/currency.
  • Production deployment architecture, automated migrations, monitoring, backup/restore drills, and performance objectives.
